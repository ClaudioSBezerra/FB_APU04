### 1. Contrato do pacote Oracle — `backend/services/oracle_fiscal.go`

23 parâmetros IN (ordem exata do bloco PL/SQL, notação nomeada):
```
pCnpjEmpresa, pUFOrigem, pUFDestino, pTipoContribuinte, pTipoCentroFiscal,
pTipoOperacao, pEntradaSaida, pProduto, pCodigoGrupoFiscal, pCnpjExcecao,
pIndicadorServico, pPrecoTotal, pDespesas, pDesconto, pIPI,
pAliquotaSimplesNacional, FornecedorSimplesNacional (SEM prefixo 'p'!),
pTipoIsencaoPedidoBonificado, pCFOPOperacao, pTipoContribuinteSecundario,
pSimulacaoCalculo, pDataReferenciaFiscal, pCodigoIbge
```
Retorno: objeto `RDADOS_FISCAIS_PRODUTO` com ~88 campos OUT (ICMS clássico,
ICMS-ST, PIS/COFINS, IPI, DIFAL/partilha, Reforma Tributária IBS/CBS UF+MUN).

**Padrão de segurança obrigatório:** bloco PL/SQL anônimo 100% estático
(nunca concatenar valores — sempre `sql.Named`/`sql.Out`/`go_ora.Out`), gerado
via reflection a partir de duas tabelas Go (`fiscalInParams`, `fiscalOutFields`)
que mapeiam nome do parâmetro Oracle ↔ campo da struct Go.

**Pegadinha #1 (go-ora):** `database/sql`'s `sql.Out{Dest: ptr}` genérico manda
`size=0` pro driver go-ora em binds OUT de string, causando
`ORA-06502 buffer too small`. Fix: usar o tipo nativo do driver,
`go_ora.Out{Dest: ptr, Size: 4000}` (import `go_ora "github.com/sijms/go-ora/v2"`),
não o `database/sql.Out` genérico.

**Pegadinha #2 (tipos):** os campos `IdRegraCalculoIcms`, `IdRegraCalculoPisCofins`,
`IdRegraCalculoIpi`, `IdRegraCalculoIbs`, `IdRegraCalculoCbs` no objeto Oracle
são **VARCHAR2** (ex.: `"IVA_N_FC01PEPE1SNVRJNE6811810030002IC61"`), não NUMBER
— tipar como `string` em Go, nunca `float64` (causa
`ORA-06502 character to number conversion error` se errado).

### 3. Execução em lote — `backend/handlers/fiscal_execution.go`

Padrão de concorrência/isolamento (mapeia direto pra TPF-05):
- Semáforo `chan struct{}` com capacidade 5 (nunca mais que 5 chamadas Oracle
  simultâneas — pool dedicado com `SetMaxOpenConns(5)`)
- `context.WithTimeout(ctx, 15*time.Second)` por item (não pro lote inteiro)
- `defer recover()` por goroutine de item — panic de um item vira `status="error"`
  persistido, nunca derruba os demais itens do lote
- Cada item é seu próprio `INSERT ... ON CONFLICT (nfe_item_id) DO UPDATE` —
  nunca uma transação única pro lote inteiro

Defaults usados quando o XML/schema atual não carrega o parâmetro (documentar
igual em TPF-03, e reavaliar já que `nfe_saidas`/`nfe_saidas_itens` do FB_APU04
pode ter mais colunas disponíveis que o schema enxuto do FB_TESTESFC tinha):
```go
defaultTipoContribuinte          = "N"     // não contribuinte
defaultTipoCentroFiscal          = "VRJNE" // valor do script de teste do pacote
defaultTipoOperacao              = 1       // operação normal de venda
defaultIndicadorServico          = "N"     // comércio, não serviço
defaultFornecedorSimplesNacional = "N"     // CRT do emitente não persistido
```

**Só o caminho "normal" foi validado contra Oracle real** — Simples Nacional,
prestação de serviço etc. podem expor default incorreto quando aparecerem
casos reais divergentes na tela de comparação (Fase 12).

- Nunca concatenar valores no bloco PL/SQL do pacote fiscal — sempre bind
  nomeado (`sql.Named`/`go_ora.Out`), mesmo padrão 100% estático do
  `oracle_fiscal.go` original.

  usar `go_ora.Out{Dest: ptr, Size: N}`.
- Nunca tipar `IdRegraCalculo*` como número — são VARCHAR2.
- Nunca abortar o lote inteiro por causa de um item com erro — isolamento por
  item é requisito (TPF-05), não um nice-to-have.
- Nunca adivinhar `cod_empresa` — erro explícito por item quando a filial não
  está mapeada.
