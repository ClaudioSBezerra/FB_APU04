**Hipótese principal (a validar no diagnóstico):**
O domínio `simu.fcxlabs.com` antes hospedou **FC Bots**, que registrou um service worker no escopo `/`. Quando o FB_APU04 substituiu FC Bots no mesmo domínio, navegadores que visitaram FC Bots ainda têm:
- O SW antigo registrado e ativo em `simu.fcxlabs.com` — intercepta `fetch('/')` e responde com cache antigo do FC Bots (HTML diferente)
- Cache Storage com entradas do FC Bots (assets antigos)

Service workers persistem entre deploys do mesmo domínio até serem explicitamente desregistrados ou substituídos por outro SW na mesma path.

**Estratégia de cleanup** (se hipótese confirmada): "kill switch" SW — apesar do nome, é um JS comum (não um SW novo) que executa no primeiro carregamento do FB_APU04 para limpar SWs e caches da origem:

```js
// unregister-sw.js — NÃO É um service worker; é vanilla JS rodando na page.
// Roda em TODO carregamento; idempotente (checa antes de tocar).
(function () {
  if ('serviceWorker' in navigator) {
    navigator.serviceWorker.getRegistrations().then(function (regs) {
      for (var i = 0; i < regs.length; i++) {
        regs[i].unregister();
      }
    }).catch(function () { /* ignore */ });
  }
  if (typeof caches !== 'undefined' && caches.keys) {
    caches.keys().then(function (keys) {
      for (var i = 0; i < keys.length; i++) {
        caches.delete(keys[i]);
      }
    }).catch(function () { /* ignore */ });
  }
})();
```

Carregamento via `<script src="/unregister-sw.js"></script>` no `<head>` ANTES do módulo Vite — script comum (não module), executa síncrono na ordem do parser.

**Contraste importante:** se o app FB_APU04 algum dia adicionar PWA/SW próprio, o `unregister-sw.js` precisa SAIR antes (caso contrário desregistraria o SW novo). Documentar essa pegadinha no SUMMARY.

**Como diagnosticar SW órfão sem acesso direto à máquina infectada:**

1. Em qualquer navegador, abrir https://simu.fcxlabs.com/login em janela ANÔNIMA (sem cache anônimo herdado), DevTools aberto na aba Application:
   - Service Workers: lista SWs registrados nesse origin
   - Cache Storage: lista cache APIs em uso
2. Em janela NORMAL (cache potencialmente sujo):
   - Application → Service Workers → ver "scope: /" e "source: ..."
   - Comparar com a janela anônima — diferença é o artefato órfão
3. Se acessível, no servidor (AWS):
   ```bash
   curl -sI https://simu.fcxlabs.com/index.html | grep -iE "cache-control|content-type|server"
   curl -s https://simu.fcxlabs.com/index.html | head -30
   ```
4. Validar headers do Coolify/Traefik:
   ```bash
   curl -sI https://simu.fcxlabs.com/ | grep -iE "x-cache|via|age|server"
   ```
   Se `Age:` presente e crescente, há cache de borda em algum lugar.

**Fontes de cache em ordem de probabilidade:**
1. **Service Worker órfão (FC Bots)** — alta probabilidade dado o contexto do domínio
2. Browser disk cache do FC Bots (forçado por algum `Cache-Control: max-age` antigo)
3. Cloudflare/CDN entre o usuário e o Traefik (se houver — não há evidência de Cloudflare no compose)
4. Coolify proxy cache (improvável; Coolify usa Traefik que, sem labels específicas, não cacheia HTML)
5. Nginx do app — descartado: `Cache-Control: no-store` já presente

**Backstop conservador (caso diagnóstico seja inconclusivo):**
- Adicionar header `Clear-Site-Data: "cache", "storage"` em `/index.html` na nginx — diz ao navegador para limpar cache+storage da origem em todo carregamento. Limitação: não é suportado por Safari ≤14 e força mais I/O do que precisa.
- Ou: o `unregister-sw.js` (cleanup script) é seguro mesmo se a causa real for outra — desregistrar SW que não existe é no-op; limpar caches que não existem é no-op. Prefira esse.
