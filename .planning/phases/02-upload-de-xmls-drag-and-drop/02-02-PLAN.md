**backend/handlers/xml_upload.go** — novo arquivo com 3 handlers:

XMLUploadHandler(db *sql.DB) http.HandlerFunc:
- Verifica r.Method; aceita apenas POST (per padrão do projeto)
- Extrai company_id via GetEffectiveCompanyID
- Lê multipart: r.ParseMultipartForm(MaxUploadBytes) — retorna 413 se maior que 100MB
- Valida Content-Length antes de processar: se > MaxUploadBytes, retorna jsonErr 413 com mensagem "Arquivo excede limite de 100MB"
- Detecta tipo de arquivo: extensão .xml ou .zip
- Se ZIP: chamar extractXMLsFromZip(data []byte) ([]namedXML, error) que usa archive/zip stdlib — ignora subpastas e arquivos não-.xml (PITFALL 4 do RESEARCH.md), valida UncompressedSize64 antes de abrir (PITFALL ZIP bomb)
- Se len(xmlFiles) > MaxXMLsPerBatch: retorna 400 com "ZIP contém N XMLs, máximo é 5000"
- Detecta tipo de nota (entradas/saidas/ctes) via parâmetro de formulário "tipo" (obrigatório: entradas|saidas|ctes)
- Cria registro em xml_upload_batches com status='pending', total_count=len(xmlFiles), uploaded_by=userID
- Se len(xmlFiles) <= BatchAsyncThreshold (50): processar inline em processXMLBatch(), retornar 200 + resultado
- Se len(xmlFiles) > 50: retornar 202 + {"batch_id": "uuid", "status": "processing", "total": N}

Função processXMLBatch(db, batchID, companyID, tipo, xmlFiles):
- Itera XMLs, para cada um: detectar modelo (55=NFe, 57=CTe), chamar handler correto
- Para NFe: reutilizar a lógica de parseNFeXML existente (call ao NfeEntradasUploadHandler ou NfeSaidasUploadHandler de forma programática — ou extrair a lógica de parse para função compartilhada)
- Atualizar xml_upload_batches.processed_count a cada 10 XMLs
- Registrar erros em error_details JSONB (acumular array de {filename, motivo})
- Ao final: UPDATE xml_upload_batches SET status='done', completed_at=NOW(), imported_count=X, rejected_count=Y

XMLUploadBatchStatusHandler(db *sql.DB) http.HandlerFunc:
- GET /api/xml/upload-batches/{id}/status
- Extrai batch_id do path
- SELECT * FROM xml_upload_batches WHERE id=$1 AND company_id=$2
- Retorna JSON com todos os campos para polling

XMLUploadBatchesHandler(db *sql.DB) http.HandlerFunc:
- GET /api/xml/upload-batches
- Query params: tipo (opcional), limit (default 20), offset (default 0)
- SELECT com paginação, ordenado por created_at DESC, filtrado por company_id
- Retorna array + total para histórico (per D-13)

**backend/worker/xml_worker.go** — novo worker para batches assíncronos (per D-15):
Seguir exatamente o padrão de backend/worker/worker.go:
- StartXMLWorker(db *sql.DB) — spawna 3 goroutines xmlWorkerLoop
- xmlWorkerLoop: SELECT id, company_id, tipo, error_details FROM xml_upload_batches WHERE status='pending' FOR UPDATE SKIP LOCKED LIMIT 1
- Se nenhum job: sleep 5s, continuar
- UPDATE status='processing'
- Chamar processXMLBatch (do xml_upload.go) com os dados do batch
- UPDATE status='done'/'failed' ao finalizar
- defer recover() para panic safety (respawna após 5s como worker.go faz)

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02-01 | Denial of Service | ZIP bomb | mitigate | Verificar f.UncompressedSize64 antes de abrir cada entry; rejeitar se soma total > MaxUploadBytes |
| T-02-02-02 | Denial of Service | XML bomb (billion laughs) | accept | encoding/xml stdlib Go não expande entidades externas por default — safe |
| T-02-02-03 | Tampering | Path traversal em ZIP | mitigate | Usar filepath.Base(f.Name) para ignorar subpastas; pular entries com ".." no nome |

| T-02-02-05 | Spoofing | Upload sem company_id | mitigate | GetEffectiveCompanyID valida relação user↔company antes de qualquer persistência |
